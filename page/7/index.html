CWE-Bench-Java：高效构建大规模漏洞挖掘数据集

发表于 2026-01-22 分类于 Java Security

在软件安全研究和漏洞挖掘（Vulnerability Mining）领域，构建高质量的数据集是第一步，也是最耗时的一步。我们需要从成千上万个开源项目（如 Apache Spark, Spring Framework）中，精准还原出几年前某个特定版本的“案发现场”。

最近在复现 IRIS 项目时，学习到了很实用的数据集构建方法，所以记录一下。

项目中的数据集构建脚本 fetch_one.py ，采用了 “浅克隆 + 精准抓取” 的 Git 组合拳。这套方案避免了下载冗余的历史记录，将构建速度提升了数倍，博客记录一下学习这套 Git 命令背后的逻辑。

面临的挑战：时间与空间的博弈

通常，想要获取某个历史版本的代码，最直接的做法是：
git clone <repo_url> 然后 git checkout <old_commit>。

但在大规模数据挖掘场景下，这种做法有两个致命弱点：

  1. 体积巨大：像 Linux 内核或 Chromium 这样的大型项目，.git 目录动辄几个 GB。如果我们要分析 1000 个项目，硬盘瞬间爆炸。
  2. 网络浪费：我们可能只需要 5 年前某次提交的那几十个文件，却下载了项目成立 10 年来的每一次变更记录。

为了解决这个问题，项目在 fetch_project 函数中设计了一套“外科手术式”的精准 fetch 操作流程。

核心流程拆解

Python 脚本并没有一次性拉取所有数据，而是分四步走：快速搭架子 -> 精准捞数据 -> 时光倒流 -> 环境修复。

第一步：极速克隆 (Clone Latest)

  • 命令：git clone --depth 1 <repo_url> <target_dir>
  • 解读：
    这是整个流程的基石。参数 --depth 1 告诉 Git：“我只要最新的这一层代码，以前的历史我都不关心。”
  • 作用：
    这被称为 浅克隆 (Shallow Clone)。它能以最小的代价（通常只有几十 MB）快速把仓库的“架子”搭好，确立远程连接，生成 .git 目录，而无需下载漫长的历史提交记录。

第二步：精准补货 (Fetch Old Commit)

  • 命令：git fetch --depth 1 origin <commit_id>
  • 解读：
    这是高阶的一步。我们已经有了仓库架子，但那个包含漏洞的 commit_id 可能深埋在 5 年前的历史中，本地并没有。
    这条命令利用了现代 Git 服务器（如 GitHub）支持的特性，直接向服务器请求：“我只想要这个特定的 Commit Hash，把它以及它的文件快照给我，其他的父节点历史我依然不要。”
  • 作用：
    这相当于“按需补货”。Git 会将这个古老的版本作为一个“孤岛”下载到本地的 .git 数据库中。既拿到了我们急需的数据，又保持了本地仓库的轻量化。

第三步：时光倒流 (Checkout)

  • 命令：git checkout <commit_id>
  • 解读：
    数据下载到了 .git 目录（通常存在 FETCH_HEAD 中），但工作区的文件还是最新的。这一步是将工作区的文件“刷新”成漏洞版本的状态。
  • 作用：
    执行后，工作区正式回到“案发时间”。此时虽然处于 Detached HEAD（头指针分离）状态，但这对于代码分析和编译来说完全足够。

第四步：修复环境 (Apply Patch)

  • 命令：git apply <patch_path>
  • 解读：
    如果我们提前准备了补丁文件（位于 data/patches/），则应用它。
  • 为什么要这步？：
    这是漏洞复现中最痛的一点——“代码虽然回去了，环境却变了”。
    老旧的代码往往引用了已经关闭的 Maven 仓库，使用了不再兼容的 Gradle 插件，或者依赖了特定版本的编译器。我们不修改业务逻辑，只通过 Patch 修改构建脚本（如 pom.xml），确保这些“老古董”代码能在现代的机器上成功编译跑起来。

3. 总结

通过这套流程，IRIS 成功构建了一个高效的数据集构建 pipeline：

  1. Clone Latest: 只拿最新版，快。
  2. Fetch Specific: 只抓特定点，准。
  3. Checkout: 切换工作区，稳。
  4. Patch: 修正构建项，活。

这套 Git 组合拳极其精妙，它将原本可能需要数小时的下载任务缩短到了几秒钟，同时极大地节省了磁盘空间。对于从事软件仓库挖掘（Mining Software Repositories, MSR）的研究者来说，这绝对是必备的最佳实践。

PS：注意需要收集到精确的 commit_id 也就是存在漏洞的 SHA-1 哈希值作为版本号。

SSH安全协议

发表于 2026-01-18 更新于 2026-08-22 分类于 Config

基础理论：Diffie-Hellman (DH) 密钥交换协议

在介绍SSH之前，首先了解DH协议，因为它是SSH能够安全协商密钥的基石。

  • 核心难题：如何在不安全的网络上，让两个人协商出一个只有他们知道的“密码”（会话密钥），而不用担心被旁人窃听？
  • 数学原理：基于离散对数问题的困难性。
    • 公式：
    • 正向计算容易：已知 ，算出 很快。
    • 反向计算极难：已知 ，想要算出指数 （私钥），在 足够大时，计算量是指数级的，现代计算机无法在有效时间内破解。
  • 作用：SSH利用DH算法，在客户端和服务器之间安全地生成一个对称密钥，用于后续的数据加密传输。

核心重点：SSH协议详解 (Secure Shell)

1. 什么是SSH？

SSH（Secure Shell）即“安全外壳”。它是基于公钥密码体系的安全应用协议，专为远程登录会话和其他网络服务提供安全性。

  • 主要目的：替代Telnet、rsh等不安全的明文传输协议。
  • 核心功能：加密（防窃听）、认证（防伪装）、完整性检查（防篡改）。

2. SSH的内部架构（三大子协议）

SSH不是一个单一的协议，而是由三个分工明确的协议组成的“协议栈”：

  1. SSH传输层协议 (Transport Layer Protocol)
    • 职责：负责最底层的脏活累活。包括算法协商（商量用什么加密）、密钥交换（DH算法）、服务器认证（确认服务器是真的）。
    • 结果：建立一个加密的、压缩的、保证完整性的安全通道。
  2. SSH用户认证协议 (User Authentication Protocol)
    • 职责：运行在传输层之上，负责鉴别客户端（用户）是谁。
    • 方式：支持口令认证（输入密码）、公钥认证（免密登录）等。
  3. SSH连接协议 (Connection Protocol)
    • 职责：在加密和认证都完成后，负责把加密隧道多路复用。
    • 功能：将一个物理连接逻辑上分为多个逻辑通道（Channel），分别处理终端会话、文件传输、端口转发等。

3. SSH的工作流程（7个步骤）

  1. 获取证书：客户端获取服务器的公钥证书（或已经存有服务器公钥）。
  2. 连接请求：客户端发起TCP连接（握手）。
  3. 服务器身份通告：服务器把自己的公钥发给客户端。
  4. 验证服务器：客户端验证这个公钥是不是真的服务器（防止中间人冒充）。
  5. 建立密钥 (DH)：双方通过Diffie-Hellman算法，协商出一个会话密钥（对称密钥）。
  6. 认证用户：建立加密隧道后，服务器验证客户端的身份（如输入密码）。
  7. 会话开始：使用SSH Tunnel进行加密通信。

4. 关键环节：如何验证服务器公钥的真实性？

客户端如何确认“发给我公钥的服务器真的是由于我要连接的那台服务器？”（防止中间人攻击）。主要有三种方法：

  • 方法一：物理拷贝 (最原始)
    • 用户直接带个U盘把服务器的公钥拷到客户端电脑里。安全但麻烦，不适合大规模使用。
  • 方法二：指纹核对 (最常用)
    • 流程：
      1. 首次连接时，客户端下载服务器公钥。
      2. 屏幕显示公钥的指纹 (Hash值)。
      3. 用户通过电话或其他渠道联系管理员核对指纹。
      4. 若指纹一致，用户输入“yes”信任该主机，公钥被保存到 known_hosts 文件中。
  • 方法三：PKI 认证 (最规范)
    • 通过权威的 CA 机构（PKI体系）来验证服务器证书的合法性。

5. SSH 的实际应用与风险

  • 默认端口：Linux系统中默认是 TCP 22 端口。
  • 功能扩展：不仅是远程黑窗口（Shell），还支持 scp/sftp（文件传输）、端口转发（跳板机/代理）。
  • 安全隐患：
    • 中间人攻击 (MITM)：如果在首次连接（TOFU, Trust On First Use）时没有仔细核对指纹，攻击者可能拦截连接并伪造公钥。
    • 拒绝服务攻击 (DoS)：因为SSH握手涉及复杂的加密计算（DH交换），消耗CPU资源大，攻击者可利用这一点耗尽服务器资源。

总结

SSH 是一个分层的协议，利用 DH算法 协商密钥，通过 三种方式 验证服务器身份，最终建立加密隧道替代 Telnet，保障 22端口 的远程管理安全。

加密与签名的区别

发表于 2026-01-18 分类于 密码学

私钥和公钥在数学逻辑上是可以“反过来”使用的（特别是在最经典的 RSA 算法中）。

但这两种“方向”所达到的安全目标是完全相反的，我们可以把这对密钥想象成一对神奇的数学钥匙：

数学原理：互为逆运算

在 RSA 这种经典的公钥密码体制中，公钥和私钥在数学上是成对生成的。

  • 规则：用A钥匙锁上的东西，只能用B钥匙打开；反之，用B钥匙锁上的东西，只能用A钥匙打开。

数学上没有规定谁必须叫“公钥”，谁必须叫“私钥”。只是在产生密钥后，我们人为地规定：

  • 公开给所有人的那把叫公钥。
  • 自己留着保密的那把叫私钥。

2. 两种方向，两种用途

正是因为它们可以“反过来”用，才衍生出了密码学的两大支柱功能：加密和签名。

情况 A：公钥加密，私钥解密（正常加密）

  • 操作：别人用你的公钥把数据锁起来。
  • 结果：因为只有你才有私钥，所以全世界只有你一个人能打开看。
  • 目的：机密性 (Confidentiality) —— 保护隐私，不让别人偷看。
  • 比喻：别人把信扔进你的信箱（公钥），只有你有钥匙（私钥）能打开信箱取信。

情况 B：私钥“加密”，公钥“解密”（数字签名）

  • 操作：你用你的私钥把一段数据（通常是摘要）锁起来（处理一下）。
  • 结果：因为公钥是公开的，全世界所有人都能用你的公钥打开它。
    • 你可能会问：“所有人都能打开，那还有什么保密性可言？”
    • 没错！这里根本不是为了保密！
    • 既然所有人都能用你的公钥解开，这就证明了——这段密文一定是用你的私钥锁上的。因为除了你的私钥，别人的私钥锁出来的东西，你的公钥是打不开的。
  • 目的：认证/防抵赖 (Authentication) —— 证明“这确实是我发的”。
  • 比喻：这就好比古代皇帝的“玉玺”（私钥）。皇帝在诏书上盖了章，全天下人（拿着公钥）一看印章纹路，就知道这是皇帝亲笔，不是别人伪造的。

3. 一个小小的专业修正

虽然我们为了理解方便，常说“数字签名就是用私钥加密”。但在严格的学术定义中：

  • 对于 RSA 算法：确实就是“私钥加密，公钥解密”的数学过程。
  • 对于其他算法（如 ECC、SM2、DSA）：虽然逻辑上是“私钥处理，公钥验证”，但数学过程并不是简单的加密反运算，而是专门设计的签名算法和验证算法。

总结：

  • 公钥 -> 私钥 = 为了秘密（只有你能看）。
  • 私钥 -> 公钥 = 为了证明（只有你能签）。

软考密码学考点概述

发表于 2026-01-18 更新于 2026-08-22 分类于 密码学

软考常考的密码学基础知识、攻击类型以及主要的密码体制。以下是重要知识点：

一、 密码学基础概念 (Overview)

  • 定义与目标：密码学是研究信息安全保护的科学。主要目标是实现信息的保密性、完整性、可用性及抗抵赖性。
  • 组成：包含 密码编码学（研究加密/保护）和 密码分析学（研究破译/获取明文）。
  • 相关法律：提及了《电子签名法》（2005年）、商用密码算法公布（2006年）及《密码法》草案（2019年）。
  • 核心术语：
    • 明文：未加密的消息。
    • 密文：加密后的消息。
    • 加/解密算法：进行变换的运算规则。
    • 密钥：控制算法操作的关键参数。

二、 密码分析与攻击类型 (Attack Types)

根据攻击者拥有的信息量（前提条件），攻击类型分为五种（按攻击者能力从低到高）：

  1. 唯密文攻击：最困难，攻击者只有密文。
  2. 已知明文攻击：攻击者拥有一些“明文-密文”对。（注：一个安全的密码必须能经得起这种攻击）。
  3. 选择明文攻击：攻击者能制造明文并获取对应的密文（对攻击者有利）。
  4. 密文验证攻击：攻击者能判断某个密文解密后的结果是否合法。
  5. 选择密文攻击：最容易破译，攻击者能选定密文并获取对应明文（常见于攻击公钥体制和数字签名）。

三、 密码体制分类 (Cryptosystems)

1. 私钥密码体制 (Symmetric Key / 对称加密)

  • 特点：加密和解密使用相同的密钥。
  • 流程：双方必须事先通过安全渠道交换密钥。
  • 优缺点：
    • 优点：速度快
    • 缺点：密钥分配困难、密钥管理量大、无法认证源（难以实现抗抵赖）。
  • 常见算法：
    • DES：替换+移位、56位密钥、64位数据块、速度快、但56位密钥易被破解
    • 3DES：三重DES，两个56位密钥，K1和K2，较DES更安全
    • AES：美国标准，替代DES，安全性高
    • IDEA：128位密钥、64位数据块、较DES加密性更好
    • RC-5：RSA 数据公司很多产品使用RC5

2. 公钥密码体制 (Asymmetric Key / 非对称加密)

  • 特点：加密和解密使用不同的密钥（公钥和私钥）。
  • 原理：
    • 公钥：公开，用于加密。
    • 私钥：保密，用于解密。
    • 例子：甲给乙发消息，用乙的公钥加密，只有乙的私钥能解密。
  • 优缺点：
    • 优点：密钥分发方便、管理量少、支持数字签名。在公钥密码体制中，仅根据密码算法和加密密钥来确定解密密钥在计算上是不可行的。
    • 缺点：速度慢，计算量大，不适合加密大数据。
  • 常见算法：
    • RSA：基于大数分解，应用最广。公钥 (e,n) 私钥 (d,n) 。
    • ECC（椭圆曲线）、Elgamal、D-H（Diffie-Hellman）、背包算法。

3. 混合密码体制 (Hybrid System)

  • 目的：结合对称加密的“快”和非对称加密的“密钥分发方便”。
  • 工作流程：
    1. 发送方随机生成一个对称密钥。
    2. 用对称密钥加密明文消息（数据传输快）。
    3. 用接收方的公钥加密这个对称密钥（数字信封）。
    4. 将加密后的消息和加密后的密钥一起发送。
    5. 接收方先用私钥解出对称密钥，再用对称密钥解密消息。

这张PPT主要详细介绍了四种常见的对称加密算法（DES、3DES、IDEA、AES）的具体参数和工作原理。以下是为您总结的核心知识点：

四、常见密码算法

1. DES 算法 (Data Encryption Standard)

  • 类型：分组加密算法。
  • 分组长度：支持 64比特 的明文块加密。
  • 密钥长度：56比特。
  • 特点：由于密钥较短（56位），在现代算力下安全性较低，已逐渐被淘汰。

2. 三重DES (3DES / TDEA)

  • 原理：为了提高安全性，使用DES算法对明文进行 “加密 - 解密 - 加密” 的三次操作。
  • 操作流程：
    • 加密：明文 -> (用K1加密) -> (用K2解密) -> (用K3加密) -> 密文。
    • 解密：密文 -> (用K3解密) -> (用K2加密) -> (用K1解密) -> 明文。
  • 密钥规则：通常情况下，K1 和 K3 是相同的密钥（即使用两个不同的密钥K1和K2进行三次运算）。

3. IDEA 算法 (International Data Encryption Algorithm)

  • 类型：分组加密算法。
  • 分组长度：明文和密文分组均为 64比特。
  • 密钥长度：128比特（比DES更安全）。
  • 设计思想：混合使用来自不同代数群中的运算。

4. AES 算法 (Advanced Encryption Standard)

AES是用来替代DES的新一代标准，PPT中列出了该算法必须满足的标准要求：

  • 公开性：算法无密级，描述必须完全公开披露。
  • 免费性：必须可以在世界范围内免费使用。
  • 分组长度：支持至少 128比特 的分组。
  • 密钥长度：支持 128、192 和 256比特 的密钥长度。

总结对比表：

算法 分组长度 密钥长度 关键特征

3DES 64 bit 112 bit* (通常) “加密-解密-加密”模式，过渡方案。
IDEA 64 bit 128 bit 混合代数运算设计。

IRIS：基于LLM辅助的静态分析检测安全漏洞

发表于 2026-01-13 分类于 SAST

软件容易受到安全漏洞的影响。用于检测这些漏洞的程序分析工具由于依赖人工标注的规范，在实践中效果有限。大型语言模型（LLM）展现出令人印象深刻的代码生成能力，但它们无法对代码进行复杂推理以检测此类漏洞，特别是因为此任务需要全仓库分析。我们提出了IRIS，一种神经符号方法，系统地结合LLM与静态分析来执行全仓库推理以检测安全漏洞。具体来说，IRIS利用LLM推断污点规范并执行上下文分析，从而减轻对人工规范和检查的需求。为了评估，我们策划了一个新数据集CWE-Bench-Java，包含120个经过人工验证的真实Java项目中的安全漏洞。最先进的静态分析工具CodeQL仅检测到其中27个漏洞，而使用GPT-4的IRIS检测到55个（+28），并将CodeQL的平均误报发现率提高了5个百分点。此外，IRIS识别出4个以前未知的漏洞，这些漏洞无法被现有工具发现。IRIS已公开发布于 https://github.com/iris-sast/iris。

📌 关键解读1：研究动机与核心贡献

核心问题

  1. 静态污点分析的局限：传统工具如CodeQL严重依赖人工标注的API规范（源、汇点、净化器），这导致：

    • 规范缺失→漏报
    • 规范不精确→误报

  2. LLM的潜力与限制：

    • LLM能理解代码但无法进行复杂的全项目推理
    • 需要结合静态分析的精确性

核心创新

IRIS提出的神经符号方法实现了三个关键突破：

  1. 自动规范推断：使用LLM从API文档和代码中推断污点源和汇点
  2. 上下文感知过滤：利用LLM理解代码上下文，减少误报
  3. 全仓库分析：结合静态分析的数据流追踪能力

1. 引言

安全漏洞对软件应用程序及其用户的安全构成重大威胁。仅在2023年，就报告了超过29,000个CVE——比2022年高出近4000个（CVE趋势）。尽管在揭示漏洞的技术方面取得了进展，检测漏洞仍然极具挑战性。

一种名为静态污点分析的有前景技术被广泛应用于流行工具中，如GitHub CodeQL、Facebook Infer、Checker Framework和Snyk Code。然而，这些工具面临几个极大限制其在实践中有效性和可访问性的挑战。

1.1 主要挑战

由于缺少第三方库API的污点规范而导致的漏报

静态污点分析主要依赖第三方库API作为源、汇点或净化器的规范。在实践中，开发人员和分析工程师必须根据他们的领域知识和API文档手动制作这些规范。这是一个费力且容易出错的过程，经常导致规范缺失和漏洞分析不完整。此外，即使这些规范可能存在于许多库中，它们也需要定期更新以捕获这些库新版本中的变化，并覆盖开发的新库。

由于缺乏精确的上下文感知和直观推理而导致的误报

众所周知，静态分析经常受到低精度的困扰，即可能产生许多虚假警报。这种不精确源于多种来源。例如，源或汇点规范可能是虚假的，或者分析可能过度近似代码中的分支或可能的输入。此外，即使规范正确，检测到的源或汇点所使用的上下文可能无法被利用。因此，开发人员可能需要筛选几个潜在的虚假安全警报，浪费大量时间和精力。

1.2 先前数据驱动方法的局限性

已经提出了许多技术来解决静态污点分析的挑战。例如，MERLIN提出了一种概率方法来自动挖掘污点规范。最近的工作Seldon通过将污点规范推断问题表述为线性优化任务来提高这种方法的可扩展性。然而，这些方法依赖于分析第三方库的代码来提取规范，这既昂贵又难以扩展。研究人员还开发了统计和基于学习的技术来缓解虚假正警报。然而，这些方法在实践中仍然效果有限。
