用URL编码机制防御路径遍历漏洞

发表于 2026-01-28 分类于 Java Security

为什么服务器会将 ..%2Fadmin 视为一个名为 “…/admin” 的普通用户名，找不到该用户，返回 404？

这是一个非常深刻且核心的计算机安全问题，涉及到 URL 编码（Percent-encoding）的本质机制。

简单来说，区别在于：/ 是指令（分隔符），而 %2F 是数据（纯文本）。

我们可以通过“信封与地址”或者“文件系统”的逻辑来拆解这个问题：

1. 核心原理：控制字符 vs 数据字符

在 HTTP 协议和 URL 标准（RFC 3986）中，某些字符具有特殊的“结构化含义”，被称为保留字符（Reserved Characters）。

  • / (斜杠)：这是一个控制字符。它的作用是告诉服务器：“当前的目录结束了，进入下一级目录”。
  • .. (双点)：配合斜杠使用时，也是控制指令。它的作用是告诉服务器：“返回上一级目录”。

当 Retrofit（默认为 encoded=false）将 / 转义为 %2F 时，它实际上是在做一件最重要的事情：“去功能化”。

2. 服务器视角的解析过程对比

假设服务器收到请求，Web 服务器（如 Nginx、Tomcat）会按照 / 来切割路径，决定把请求路由到哪里。

场景 A：攻击成功（未编码）

URL: http://example.com/users/../admin/profile

  1. 服务器看到第一个 /：进入 users 目录。
  2. 服务器看到第二个 /：发现前面是 ..。
    • 指令生效：服务器执行“回退”操作，跳出了 users 目录，回到了根目录。
  3. 服务器继续解析：进入 admin 目录。
  4. 结果：最终访问的是 /admin/profile。

场景 B：防御成功（已编码）

URL: http://example.com/users/..%2Fadmin/profile

  1. 服务器扫描 URL，寻找分隔符 /。
  2. 关键点：服务器不认识 %2F 是分隔符。对服务器来说，%2F 只是三个普通的字符：%、2、F。它们和 a、b、c 没有任何区别。
  3. 服务器的解析逻辑如下：
    • 第一段：users（进入该层级）。
    • 第二段：读取下一个 / 之前的所有内容。这块内容是：..%2Fadmin。
  4. 路由决策：
    • 服务器会在 users 的上下文里，寻找一个名字叫 ..%2Fadmin 的资源。
    • 注意：它不是寻找一个叫 .. 的文件夹，也不是寻找一个叫 admin 的文件夹。
    • 它是在找单个文件/资源，这个资源的完整名字就叫 ..%2Fadmin（或者解码后叫 ../admin）。

3. 为什么是 404？

因为在数据库或业务逻辑中，肯定不存在一个用户的名字叫 ../admin。

  • 你的后端逻辑大概是这样的：SELECT * FROM users WHERE username = ?
  • 传入的参数是："../admin"
  • 数据库查询结果：空。
  • 服务器返回：404 Not Found（用户不存在）。

最重要的是：请求依然是被路由到了 getUser 这个接口，而没有跳转到 getAdmin 接口。

4. 总结：买火车票的隐喻

想象去火车站买票：

  • 未编码（漏洞）：你递给售票员一张纸条，上面写着：“我要去上海/..”。

    • 售票员（服务器）看到 /，理解为分隔。
    • 先定位到“上海”，然后看到“..”，于是退回上一级。
    • 结果：可能卖给了你一张起步站的票，或者把你送到了错误的地方。

  • 已编码（安全）：你把 / 进行了打包（编码），装进一个盒子里。纸条写着：“我要去【上海%2F..】”。

    • 售票员看到这只是一个地名。
    • 他在系统里搜索名为“上海/..”的城市。
    • 系统提示：查无此地（404）。
    • 安全：因为他没有执行“退回”这个动作，只是在傻傻地找一个名字很奇怪的城市。

这就是为什么 %2F 能够防御路径遍历的根本原因。

Zip Slip目录遍历漏洞

发表于 2026-01-28 分类于 Java Security

Zip Slip 是一个广泛存在且危害极大的目录遍历（Directory Traversal）漏洞。它主要发生在应用程序解压压缩文件（如 ZIP, TAR, JAR, WAR, APK 等）的过程中。

如果应用程序没有对压缩包内文件的名称进行严格的合法性校验，攻击者就可以通过构造恶意的压缩包，让解压程序将文件写入到意料之外的位置（例如覆盖系统关键文件或代码文件），从而导致远程代码执行（RCE）。

下面记录一下这个漏洞的原理、攻击方式、代码示例以及修复方案。

1. 核心原理：目录遍历

Zip Slip 的核心在于利用文件路径中的特殊字符 ../（点点斜杠）。

在操作系统中，../ 代表“上一级目录”。

  • 正常的文件名：photo.jpg
  • 恶意的文件名：../../../../var/www/html/evil.php

攻击流程如下：

  1. 构造恶意包：攻击者创建一个压缩包，在其中包含一个文件名被修改为包含大量 ../ 的文件（例如 ../../evil.sh）。
  2. 上传/传输：攻击者将这个压缩包上传到受害者的服务器（例如头像上传、文档导入功能）。
  3. 解压过程（漏洞触发点）：
    • 服务器接收到文件，准备解压到指定目录（例如 /app/uploads/）。
    • 程序读取压缩包内的文件名 ../../evil.sh。
    • 程序将“目标目录”与“文件名”拼接：/app/uploads/ + ../../evil.sh。
    • 结果：操作系统解析这个路径后，实际指向的是 /app/evil.sh（跳出了 uploads 目录）。
  4. 文件覆盖：如果程序没有检查路径，它就会将恶意文件写入 /app/evil.sh，可能会覆盖掉该位置原有的关键文件，或者写入一个恶意的 Web Shell。

2. 为什么会发生？（代码层面的原因）

很多开发者在使用编程语言（Java, Python, JavaScript, Go 等）的标准库进行解压操作时，往往只关注“拼接路径”和“写入文件”，而忽略了验证文件名的安全性。

3. 漏洞危害

Zip Slip 的危害取决于受害者服务器的权限和被覆盖文件的位置：

  1. 远程代码执行 (RCE)：
    • 这是最严重的后果。攻击者可以覆盖网站的可执行脚本（如 .php, .jsp, .asp），或者覆盖系统二进制文件。当服务器下次运行这些文件时，就会执行攻击者的恶意代码。
  2. 配置文件覆盖：
    • 攻击者可以覆盖数据库配置文件、系统设置文件，导致服务瘫痪或接管系统权限。
  3. 拒绝服务 (DoS)：
    • 通过覆盖关键的系统库文件导致系统崩溃或无法启动。

4. 影响范围

Zip Slip 并不是某一个特定软件的漏洞，而是一种由于编码习惯不良导致的设计模式漏洞。

它由安全公司 Snyk 在 2018 年大规模披露，当时发现影响了数千个开源项目，包括：

  • Java 生态：Spring, Hadoop, Spark, ElasticSearch 等。
  • JavaScript 生态：npm 上的多个解压库。
  • Python, .NET, Go 等语言的解压库或应用。

凡是允许用户上传压缩包并在服务端解压的应用，如果使用了未加固的解压代码，都可能受到影响。

5. 修复与防御方案

要修复 Zip Slip，核心逻辑是：在写入文件之前，必须校验最终的绝对路径是否以预期的目标目录开头。

  1. 输入验证：不要信任压缩包内的文件名，在代码层面强制进行“规范路径（Canonical Path）”检查。
  2. 最小权限原则：运行解压服务的用户不应拥有覆盖系统敏感文件（如 /etc/, /bin/）或 Web 根目录代码的权限。
  3. 使用安全的库：现在许多现代的解压库（如 Java 的 commons-compress 更新版）可能已经内置了防护，或者提供了更安全的 API。使用经过审计的第三方库通常比自己手写解压循环要安全。

Wildfly CVE-2018-1047 漏洞研究

发表于 2026-01-28 分类于 Java Security

CVE-2018-1047 是一个存在于 WildFly（JBoss EAP 的上游项目）中关于 Undertow 子系统的路径遍历漏洞。

WildFly（前身是著名的 JBoss AS）是由 Red Hat 领导开发的开源、轻量级且高性能的 Java EE / Jakarta EE 应用服务器；它是商业级产品 JBoss EAP（Enterprise Application Platform）的上游社区版本，以模块化架构、极速启动和低内存占用著称，广泛用于开发和部署企业级 Java 应用程序。
针对 CVE-2018-1047 的详细复盘与代码分析：

1. 漏洞基本信息

  • 漏洞编号：CVE-2018-1047
  • 漏洞组件：JBoss EAP / WildFly (具体位于 undertow 扩展模块)
  • 漏洞类型：Path Traversal (路径遍历)
  • 漏洞场景：涉及 Deployment Overlays (部署覆盖) 功能时触发。
  • 漏洞版本：9.x 和 11.0.0.Final

2. 什么是 Deployment Overlays？

在分析代码前，需要理解这个业务背景。WildFly 允许管理员配置“Overlay”，即用服务器上的外部文件覆盖 WAR 包内的静态资源，而无需重新打包 WAR。

  • 正常逻辑：用户请求 /images/logo.png -> WildFly 发现有 Overlay -> 读取 /opt/wildfly/overlays/custom-logo.png 返回。
  • 应用里原本有 logo.png。
  • 管理员配置一个 Overlay，指向 /etc/wildfly/custom-logo.png。
  • 当用户访问 logo.png 时，服务器会读取 Overlay 指定的文件。
  • 漏洞逻辑：用户请求 /images/../../etc/passwd -> WildFly 未经检查直接拼接路径 -> 读取 /etc/passwd 返回。

3. 代码分析

我们对照补丁代码（Diff）进行详细解读：

3.1. 漏洞成因

  • 问题核心：代码完全信任了变量 p。
  • JBoss VFS 的行为：overlay.getChild(p) 在处理包含 ../ 的路径时，会忠实地解析为父级目录。
  • 缺失的检查：代码只问了“文件存在吗？(exists())”，而没有问“文件还在 Overlay 目录下吗？”。这导致攻击者可以逃逸出 Overlay 定义的文件夹。

3.2. 修复逻辑

修复方案采用了非常标准的“净化 + 验证”双重防御机制：

第一层防御：路径规范化 (Canonicalization)

  • 作用：将 /images/../secure/file 转换为 /secure/file。这能防御简单的字符串拼接攻击，确保后续处理的是纯净路径。

第二层防御：边界逃逸检测 (Boundary Check) —— 这是修复的关键！

  • 原理：getPathNameRelativeTo(parent) 方法的逻辑通常是：检查 parent 的路径是否是 child 路径的前缀。
  • 效果：
    • 如果是正常请求：child 为 /opt/overlay/img.png，overlay 为 /opt/overlay。前缀匹配成功。
    • 如果是攻击请求：child 解析后变成 /etc/passwd，overlay 为 /opt/overlay。/etc/passwd 不以 /opt/overlay 开头，方法抛出异常。

4. 攻击复现推演

假设服务器上配置了一个 Overlay 目录指向 /var/www/html/overlay。

  1. 攻击者发送请求：
    GET /context-path/..%2F..%2F..%2F..%2Fetc%2Fpasswd

  2. 修复前 (Vulnerable)：

    • p = ../../../../etc/passwd
    • overlay.getChild(p) 解析指向 /etc/passwd。
    • child.exists() 返回 true。
    • 结果：服务器读取并输出 /etc/passwd 的内容。

  3. 修复后 (Patched)：

    • canonical = ../../../../etc/passwd (或者被工具类处理得更干净，但这不重要)。
    • child 依然指向 /etc/passwd。
    • 执行 child.getPathNameRelativeTo(overlay)。
    • 系统判断：/etc/passwd 不是 /var/www/html/overlay 的子文件。
    • 抛出 IllegalArgumentException。
    • 结果：Catch 块捕获异常，循环继续或结束，用户收到 404 或 403，攻击失败。

2.1. 漏洞代码（修复前）

场景假设：

  3. 执行意料之外的 JSP：攻击者甚至可能利用此漏洞去包含或执行某些不应该被直接访问的 JSP 文件。

3.1. 修复代码（修复后）

3.2. 修复逻辑解读

开发者采取了最彻底的防御措施：

  1. 切断输入源：不再读取 request.getPathInfo()。无论用户在 URL 里输入什么花哨的 ../ 或恶意路径，这个方法现在只返回字符串 "Wiki.jsp"。
  2. 强制路由：这意味着该 URL 构造器现在强制所有相关的请求都由 Wiki.jsp 这个主入口文件来处理。

这个修复表明，原本在这里使用 getPathInfo() 可能是一个设计上的疏忽或者过度灵活的设计。对于 DefaultURLConstructor 来说，将请求转发给统一的入口 Wiki.jsp 才是符合预期的行为，而不需要动态地根据 URL 路径去决定转发目标。

4. 总结与启示

这个漏洞修复案例给开发者提供了两条重要的安全经验：

  1. Input Validation (输入验证) vs. Hardcoding (硬编码)：
    通常我们说要对输入做清洗（比如过滤 ..），但在这个案例中，开发者发现根本不需要这个输入。
    启示：在修复漏洞时，首先思考“我们真的需要这个用户输入吗？”。如果可以用硬编码的白名单值（如 "Wiki.jsp"）代替动态输入，安全性得到保障。

  2. getPathInfo() 的陷阱：
    在 Java Web 开发中，request.getRequestURI() 和 request.getPathInfo() 都是攻击者可控的“污染源”。如果将它们直接传递给文件操作或 RequestDispatcher，极大概率会导致路径遍历或服务端请求伪造（SSRF）漏洞。

Vertx-Web CVE-2018-12542 漏洞研究

发表于 2026-01-28 分类于 Java Security

【漏洞分析】当 Linux 思维遇上 Windows：Vert.x Web 路径遍历漏洞 (CVE-2018-12542)

在跨平台开发中，文件路径分隔符的差异往往会被开发者忽略，而这正是大量产生安全漏洞的地方，blog 基于 CVE-2018-12542 的修复代码，分析 Vert.x Web 框架在 Windows 环境下是如何因为处理路径分隔符不当，导致目录遍历漏洞的。

1. 漏洞背景

Vert.x Web 是 Eclipse Vert.x 生态系统中用于构建现代 Web 应用的组件。其中的 StaticHandler 用于处理静态资源的访问（如 HTML、JS、图片等）。

2018 年，安全研究人员发现 Vert.x Web 的 StaticHandler 存在一个路径遍历（Directory Traversal）漏洞，CVE 编号为 CVE-2018-12542。

影响范围：

  • 版本 3.0.0 到 3.5.3
  • 使用 StaticHandler 处理静态文件。
  • 服务器运行在 Windows 操作系统上。
  • 攻击者可以读取 Web 根目录之外的任意文件（如 C:\Windows\win.ini）。

2. 核心成因：操作系统的“方言”差异

在分析代码之前，需要理解两个前置知识点：

  1. 路径分隔符：

    • Linux/Unix：只识别正斜杠 / 作为目录分隔符。
    • Windows：虽然官方推荐反斜杠 \，但同时也兼容正斜杠 /。也就是说，在 Windows API 中，..\ 和 ../ 都代表“上一级目录”。

  2. 防御机制的疏漏：
    Web 服务器通常会使用一个工具方法（如 removeDots）来清洗路径中的 ../，防止用户跳出目录。但是，如果这个工具方法是按 Linux 思维写的，只过滤了 /，却忽略了 \，那么在 Windows 上就会出事。

3. 代码修复分析 (Code Review)

仔细观察官方的修复补丁（Commit Diff）：

文件：vertx-web/src/main/java/io/vertx/ext/web/handler/impl/StaticHandlerImpl.java

修复前的代码（存在漏洞）

逻辑流：

  1. 获取请求路径。
  2. urlDecode：进行 URL 解码（例如将 %2e 变为 .，%5c 变为 \）。
  3. removeDots：清洗路径中的点号。

问题在哪里？
假设攻击者发送请求：GET /static/..%5c..%5cwindows/win.ini

  1. URL 解码后变成：/static/..\..\windows/win.ini。
  2. 传入 removeDots。此时，如果 removeDots 的实现逻辑只认 ../（正斜杠），那么它会认为 ..\ 只是普通字符，不会将其移除。
  3. 最终 path 保留了 ..\。
  4. 当这个 path 传递给 Windows 的文件系统 API 时，Windows 认为 ..\ 有效，于是成功跳转到上层目录，读取敏感文件。

修复后的代码（安全）

修复逻辑详解

修复的核心在于“归一化”（Normalization）。

  1. 环境检测：
    if (File.separatorChar != '/')
    这行代码巧妙地判断了当前运行环境。如果是 Windows，File.separatorChar 是 \，条件成立。

  2. 统一格式：
    path = path.replace(File.separatorChar, '/')
    这一步非常关键。它强制将路径中所有的反斜杠 \ 转换成正斜杠 /。

    • 攻击输入：..\..\windows\win.ini
    • 转换结果：../../windows/win.ini

  3. 安全清洗：
    path = Utils.removeDots(path)
    现在，路径中的 ..\ 变成了 ../。此时再调用通用的 removeDots 方法，它就能准确识别出这是“上级目录跳转”，并将其安全地移除或拒绝。

4. 攻击复现推演

场景：服务器运行在 Windows 上，Web 根目录为 C:\app\webroot\。

  1. 攻击者请求：http://target.com/static/..%5c..%5cWindows\System32\drivers\etc\hosts
  2. URL 解码：得到字符串 ..\..\Windows\System32\drivers\etc\hosts。
  3. 漏洞版本处理：
    • removeDots 看不懂 \，认为无需过滤。
    • 最终读取文件：C:\app\webroot\..\..\Windows\System32\drivers\etc\hosts。
    • 操作系统解析后实际指向：C:\Windows\System32\drivers\etc\hosts -> 读取成功！
  4. 修复版本处理：
    • 检测到 Windows 环境，将 \ 替换为 /。
    • 字符串变为：../../Windows/System32/drivers/etc/hosts。
    • removeDots 识别出 ../，将其消除。
    • 最终路径变为（取决于 removeDots 的具体实现，可能是空或根）：/Windows/System32/drivers/etc/hosts（但在受限的 webroot 下找不到该文件）或者直接报错 -> 攻击失败！

5. 总结与启示

CVE-2018-12542 漏洞总结：

  1. 跨平台兼容性不仅仅是功能问题，更是安全问题。在处理文件路径时，必须考虑不同操作系统对分隔符定义的差异。
  2. 防御顺序很重要：解码 -> 归一化 -> 过滤/校验。
    • 必须先解开 URL 编码。
    • 必须先将各种奇形怪状的分隔符（\）统一成标准格式（/）。
    • 最后才进行危险字符（..）的过滤。
  3. 不要假设标准库能处理所有情况：这里的 Utils.removeDots 可能是一个通用的跨平台库，但它如果没有考虑到 Windows 的 \ 混淆绕过，就需要调用方在传入之前手动进行归一化处理。

Hutool CVE-2018-17297 漏洞研究

发表于 2026-01-28 分类于 Java Security

Hutool CVE-2018-17297 目录遍历漏洞研究

1. 概述

Hutool 是一个在 Java 开发中非常流行的工具库，它提供了大量静态方法来简化开发步骤。然而，在其 4.1.12 版本及之前，ZipUtil 工具类在处理压缩文件解压时，未对文件名进行严格的路径清洗，导致了 Zip Slip（压缩包路径遍历） 漏洞。

该漏洞的 CVE 编号为 CVE-2018-17297。攻击者可以通过构造恶意的压缩包，在解压时覆盖服务器上的任意文件，严重时可导致远程代码执行。

2. 漏洞原理：什么是 Zip Slip？

Zip Slip 是一种利用压缩文件提取过程的目录遍历漏洞。

正常流程

通常，当我们解压一个文件时，预期的逻辑是将文件写入到指定的目标目录下：

  • 目标目录：/app/data/
  • 压缩包内文件：image.png
  • 最终路径：/app/data/image.png

攻击流程

Zip 协议允许文件名中包含路径字符。攻击者可以构造一个文件名包含大量 ../（上级目录跳转符）的恶意压缩包：

  • 目标目录：/app/data/
  • 恶意文件名：../../../../etc/passwd
  • 拼接路径：/app/data/../../../../etc/passwd

如果在代码层面直接使用 TargetDir + FileName 进行拼接并写入，操作系统会自动解析路径中的 ../，最终文件会被写入到 /etc/passwd，从而跳出了原本限制的 /app/data/ 目录。

3. 代码修复分析 (Fix Code Analysis)

通过查看 Hutool 官方针对该漏洞的提交记录 https://github.com/chinabugotech/hutool/commit/8d7d0b7fb5ea4f7447b40131bffc1ec506a6528e ，我们可以清晰地看到修复逻辑。

关键点解析：为什么是 getCanonicalPath？

在 Java 中，处理文件路径通常有两个方法：

  • getAbsolutePath(): 获取绝对路径。它只是简单的路径拼接，不会解析 ../。
    • 例如：/app/data/../../etc/passwd
  • getCanonicalPath(): 获取规范路径。它会解析所有的 . 和 .. 以及符号链接，返回物理文件系统上的真实唯一路径。
    • 例如：/etc/passwd

修复逻辑详解：

  1. 代码分别获取了“预期的父目录”和“实际的子文件”的规范路径。
  2. 假设父目录是 /app/data。
  3. 假设攻击者传入的文件名是 ../../etc/passwd，拼接后通过 getCanonicalPath() 解析，得到的路径是 /etc/passwd。
  4. 代码检查：/etc/passwd 是否以 /app/data 开头？
  5. 结果：显然不是。于是抛出 IllegalArgumentException，中断解压过程，从而拦截了攻击。

4. 总结与思考

CVE-2018-17297 是一个非常教科书式的输入验证漏洞。它提醒我们在开发过程中：

  1. 永远不要信任用户的输入：不仅是 Web 表单的参数，文件内容（包括文件名）也是外部输入的一部分，必须进行校验。
  2. 文件操作的安全性：在进行文件读写（特别是解压、文件上传）时，必须严格限制操作范围，防止路径逃逸。
  3. 正确使用 API：在 Java 中防御此类攻击，getCanonicalPath() 配合 startsWith() 是标准的防御范式。

Retrofit CVE-2018-1000850 漏洞研究

发表于 2026-01-28 更新于 2026-01-29 分类于 Java Security

1. 漏洞简介

CVE-2018-1000850 是 Retrofit 2.4.0 及以下版本中存在的一个高危路径遍历 (Path Traversal) 漏洞。

Retrofit 是 Android 和 Java 开发中广泛使用的 HTTP 客户端库。当开发者在使用 @Path 注解定义 URL 参数时，如果错误地将 encoded 属性设置为 true，且参数值包含不可信的用户输入，攻击者可以通过传入包含 ../ 的 payload 来“逃逸”出预期的 URL 路径结构，从而访问未授权的 API 端点，甚至导致敏感数据泄露。

2. 漏洞原理分析

核心成因：信任导致的失控

Retrofit 在构建请求 URL 时，通过 RequestBuilder 类处理 @Path 注解的参数替换。

  • 默认安全模式 (encoded = false)：Retrofit 会对参数值进行标准的 URL 编码（Percent-encoding）。例如，/ 会被转义为 %2F，.. 虽然保留，但因为没有斜杠配合，它只是一个普通的路径片段文件名，不会触发路径跳转。
  • 高危模式 (encoded = true)：这个设置告诉 Retrofit：“开发者已经处理好编码了，请原样拼接”。此时，Retrofit 完全信任输入内容，不会对 / 等特殊字符进行转义。

漏洞链条：

  1. 攻击者输入 ../secret。
  2. 因为 encoded = true，Retrofit 将其原样拼接到 URL 中。
  3. 最终生成的 URL 变成了 http://api.com/user/../secret。
  4. 当下层 HTTP 客户端（如 OkHttp）或服务端收到请求时，会遵循 URL 规范解析路径，.. 抵消了上一级目录，导致实际请求指向了 /secret。

    • OkHttp 的 HttpUrl 解析器在处理请求时，标准化路径（Path Normalization），执行 .. 的语义，导致路径发生实质性改变。
