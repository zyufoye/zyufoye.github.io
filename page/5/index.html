1. 漏洞核心原理：盲目的 “Exists” 检查

在修复之前，ClassPathResourceHandler.java 和 ExternalResourceHandler.java 的逻辑非常简单，甚至可以说过于单纯。

漏洞代码逻辑（Before）：

攻击场景：
假设开发者配置了静态文件目录为 /var/www/public

  1. 正常请求：用户请求 /style.css。系统查找 /var/www/public/style.css -> 存在 -> 返回文件。
  2. 攻击请求：用户请求 /../../../../etc/passwd（URL编码后）。
  3. 解析过程：
    • Spark 将请求路径拼接到根目录：/var/www/public/../../../../etc/passwd。
    • 操作系统或 Java 的 File 类解析这个路径。.. 代表上一级目录，路径被“标准化”解析为 /etc/passwd。
  4. 漏洞触发：
    • 旧代码执行 resource.exists()。
    • 由于 /etc/passwd 确实存在于磁盘上，函数返回 true。
    • Spark 直接把 /etc/passwd 的内容发给了攻击者。

根本原因：旧代码只关心“文件在不在”，完全没有校验“文件还在不在我允许的文件夹里”。

2. 修复方案分析：引入“路径校验” (Path Confinement)

修复后的代码引入了一个全新的类 DirectoryTraversal.java，并强制所有静态文件请求必须通过这个类的检查。

A. 新增防御类 DirectoryTraversal.java

这是修复的核心。它定义了两个静态方法：

  1. protectAgainstInClassPath (针对 JAR 包内资源)
  2. protectAgainstForExternal (针对磁盘文件资源)

3. 为什么这样能修好？

让我们回到刚才的攻击场景：

  1. 攻击者请求：/../../../../etc/passwd
  2. 解析路径：Java 解析出的 resource.getPath() 绝对路径变成了 /etc/passwd。
  3. 安全检查：
    • StaticFilesFolder.external() (允许的根目录) 是 /var/www/public。
    • 代码执行检查："/etc/passwd".startsWith("/var/www/public") ?
    • 结果为 False。
  4. 结果：抛出异常，拦截请求。

4. 总结与启示

GitHub 中的漏洞修复 Diff 展示了 Java 中防御目录遍历的标准范式（Best Practice）：

  1. 不要相信输入：永远不要直接使用用户传来的路径去读取文件。
  2. 路径标准化 (Canonicalization)：在比较路径之前，必须解析所有的 ..、. 和符号链接（Java 中通常用 getCanonicalPath()，虽然这里Spark用了自定义的 startsWith 逻辑，原理类似）。
  3. 白名单前缀检查：
    • 错误做法：检查路径里有没有 .. (容易被绕过)。
    • 正确做法：最终解析出来的绝对路径，必须以限定的 Base 路径开头。

关于 Java 中的静态资源的学习

我一直认为“Java 就是写逻辑、查数据库的”，并不理解读取静态资源的作用。简单来说：如果没有静态资源，Web 世界将只剩下纯文本，没有排版、没有图片、也没有交互。

1. 什么是静态资源？

在 Web 开发中，静态资源指的是那些不需要经过服务器动态计算或处理，原本长什么样，发给浏览器就是什么样的文件。

主要包括以下几类：

  • HTML：网页的骨架（比如 index.html）。
  • CSS：网页的“皮肤”和排版（比如 style.css，决定按钮是蓝色的、文字居中）。
  • JavaScript (JS)：网页的交互逻辑（比如 app.js，点击按钮弹出窗口、发送 AJAX 请求）。
  • 图片/媒体：Logo、照片、图标、字体文件（logo.png, font.woff）。

2. 为什么 Java Web 框架需要读取它们？

我们可能会想：“Java 只要负责算出数据（比如 JSON）给前端不就好了吗？”

但在很多场景下，Java 应用不仅是一个 API 提供者，它还是一个完整的 Web 服务器。

原因一：为了让浏览器能“看到”完整的网页

浏览器请求访问 http://localhost:8080/index.html 时，服务器（Java 程序）必须去硬盘或者 JAR 包里找到这个 index.html 文件，并把它把读取出来，通过网络发送给浏览器。

如果 Java 框架没有“读取静态资源”的功能，浏览器就拿不到 HTML，用户就什么都看不见。同理，如果拿不到 CSS，网页就是乱的；拿不到 JS，网页就是死的。

原因二：开发便利性（开箱即用）

像 Spark Java、Spring Boot 这种现代框架，都追求开发效率。

  • 如果没有这个功能：想写一个带简单页面的小系统，得先装一个 Nginx 或 Apache 服务器来托管 HTML/CSS，再启动一个 Java 服务器写逻辑，然后配置跨域……这太麻烦了。
  • 有了这个功能：把 HTML/CSS 往项目的 resources 文件夹里一扔，启动 Java 程序，就可以直接访问了。这对于开发测试、小型应用、管理后台非常重要。

原因三：打包分发的便捷（All-in-One）

代码里的 local 变量，它支持从 Classpath 读取。这意味着我们可以把 HTML/CSS/JS 全部打进一个 .jar 文件里。

  • 好处：交付给客户时，只需要给一个 jar 包，运行起来就是一个带完整界面的 Web 系统。不需要告诉客户“请先安装 Web 服务器，再配置路径…”。

3. 这是所有 Java Web 框架的标配吗？

是的，基本上 99% 的 Java Web 框架都具备这个功能。
无论是老牌的 Servlet/JSP、Struts，还是现代的 Spring Boot、Spark Java、Javalin，它们都内置了静态资源处理器（ResourceHandler）。

4. 进阶视角：什么时候 Java 不应该读取静态资源？

虽然 Java 框架具备这个功能，但在大型互联网公司的生产环境中，我们通常不会让 Java 去干这件事。

为什么？

  • Java 很“贵”：Java 的强项是处理复杂的业务逻辑（算钱、处理订单、查数据库）。读取文件并发送给浏览器这种简单的 IO 操作，Java 虽然能做，但有点“大材小用”，而且消耗 Java 虚拟机的线程和内存。
  • Nginx 更专业：在生产架构中，我们通常会在 Java 前面挡一层 Nginx 或者使用 CDN。
    • Nginx 专门做静态文件服务，性能极高，并发能力极强。
    • CDN 把图片缓存到离用户最近的节点。

架构演变图：

  1. 单体/开发模式（Spark 项目）：

    浏览器 -> Java (Spark) -> [处理逻辑 + 读取 CSS/JS/图片]

  2. 生产/高性能模式：

    浏览器 -> Nginx (如果请求是图片/CSS/JS，直接返回)

             |
         (如果请求是API数据) -> **Java (Spark)** -> [只处理业务逻辑]

总结

代码里的 StaticFilesFolder 存在的意义是：

让 Spark Java 具备独立对外提供完整 Web 服务（不仅仅是 API，还包括页面和图片）的能力。这对于快速开发、独立部署微服务、或者构建自包含的 Web 应用是必不可少的基础设施。

Spark CVE-2018-9159 漏洞研究

发表于 2026-01-27 更新于 2026-01-28 分类于 Java Security

Spark (SparkJava) 是一个受 Ruby 框架 Sinatra 启发的 Java 微型 Web 框架。它以轻量级、声明式和快速开发著称，常用于构建微服务、Web API 和小型 Web 应用程序。由于其简洁的 API 设计（如 get("/hello", (req, res) -> "Hello World");），它在 Java 开发者中非常流行。

漏洞概述

  • CVE编号：CVE-2018-9159
  • 漏洞名称：SparkJava 静态资源目录遍历漏洞 (Directory Traversal)
  • 影响版本：Spark < 2.7.2 (即 2.7.1 及以下版本)
  • 简要描述：
    在 SparkJava 处理静态文件资源（Static Files）时，没有对用户请求的路径进行充分的合法性校验。攻击者可以通过构造包含 ../（父目录跳转符）的恶意 URL，跳出开发者指定的静态资源根目录，读取服务器文件系统上的任意文件（取决于运行权限），造成敏感信息泄露。

Java项目标准目录布局

发表于 2026-01-27 分类于 Java

Java 生态系统中（特别是基于 Maven 和 Gradle 构建工具）通用的标准目录布局（Standard Directory Layout）是通用的，这里简单记录一下。

这种“约定优于配置”（Convention over Configuration）的设计，使得任何接手项目的 Java 程序员都能第一时间知道代码在哪里，配置文件在哪里。

1. main 和 test 的核心区别

简单来说：main 是给用户用的（生产环境），test 是给你自己用的（开发验证环境）。

📂 src/main (主程序目录)

这是项目的核心。这里的代码和资源最终会被编译、打包（成 JAR 或 WAR 包），并部署到服务器或交付给客户。

  • 作用：存放业务逻辑、应用程序配置、网页静态资源等。
  • 后果：如果你在这里写了 bug，用户就会遇到 bug。

📂 src/test (测试程序目录)

这是项目的质检部门。这里的代码是用来验证 main 里面的代码是否正确的。

  • 作用：存放单元测试（Unit Tests）、集成测试、测试用的模拟数据等。
  • 后果：这里的代码不会被打包到最终的发布版本中。它只在构建（Build）阶段运行。如果测试失败，项目通常会打包失败，从而防止 bug 上线。

2. 标准 Maven 项目结构图

一个标准的 Maven 项目结构通常如下所示：

3. 详细目录解读

A. src/main/java

  • 这是你写 Java 业务代码的地方。
  • 通常需要按照包名（Package）建立文件夹结构，例如 com.company.project。

B. src/main/resources

  • 存放非 Java 代码的文件。
  • 常见内容：
    • application.properties 或 application.yml (Spring Boot 配置文件)。
    • log4j2.xml / logback.xml (日志配置)。
    • MyBatis 的 Mapper XML 文件。
    • SSL 证书、国际化文件等。
  • 打包后：这些文件会被直接复制到 CLASSPATH 的根目录下。

C. src/test/java

  • 存放 JUnit 或 TestNG 的测试类。
  • 最佳实践：这里的包路径通常与 src/main/java 保持一致。
    • 例如：主代码在 com.example.service.UserService
    • 测试代码在 com.example.service.UserServiceTest
    • 这样测试类可以直接访问主类中 protected 修饰的方法（包级私有）。

D. src/test/resources

  • 存放只在测试时生效的配置。
  • 场景：
    • 生产环境（main/resources）用的是 Oracle 数据库配置。
    • 测试环境（test/resources）为了速度，配置一个 H2 内存数据库。
  • 测试运行时，这里的配置优先级通常会覆盖 main 里的配置，或者专门用于测试环境读取。

E. pom.xml (Project Object Model)

  • 这是 Maven 项目的核心配置文件。
  • 它定义了：
    • 项目的基本信息（groupId, artifactId, version）。
    • 依赖（Dependencies）：你需要用到的第三方库（如 Spring, MySQL Driver, JUnit）。
    • 插件（Plugins）：如何编译、如何打包、如何运行测试。

F. target/

  • 这是 Maven 自动生成的目录，不要手动去改里面的文件，也不要提交到 Git 仓库（应该在 .gitignore 中忽略它）。
  • 当你运行 mvn clean 时，这个文件夹会被删除。
  • 当你运行 mvn package 时，编译好的 .class 文件和最终的 .jar 包会出现在这里。

总结

  • main 是为了“跑起来”
  • test 是为了“跑得稳”
  • Maven 结构 是一种全行业通用的“收纳整理术”，遵守这个结构，你的项目在任何 IDE（IntelliJ IDEA, Eclipse, VS Code）里都能被自动识别并正确运行。

CWE-Bench-Java：高效构建大规模漏洞挖掘数据集

发表于 2026-01-22 分类于 Java Security

在软件安全研究和漏洞挖掘（Vulnerability Mining）领域，构建高质量的数据集是第一步，也是最耗时的一步。我们需要从成千上万个开源项目（如 Apache Spark, Spring Framework）中，精准还原出几年前某个特定版本的“案发现场”。

最近在复现 IRIS 项目时，学习到了很实用的数据集构建方法，所以记录一下。

项目中的数据集构建脚本 fetch_one.py ，采用了 “浅克隆 + 精准抓取” 的 Git 组合拳。这套方案避免了下载冗余的历史记录，将构建速度提升了数倍，博客记录一下学习这套 Git 命令背后的逻辑。

面临的挑战：时间与空间的博弈

通常，想要获取某个历史版本的代码，最直接的做法是：
git clone <repo_url> 然后 git checkout <old_commit>。

但在大规模数据挖掘场景下，这种做法有两个致命弱点：

  1. 体积巨大：像 Linux 内核或 Chromium 这样的大型项目，.git 目录动辄几个 GB。如果我们要分析 1000 个项目，硬盘瞬间爆炸。
  2. 网络浪费：我们可能只需要 5 年前某次提交的那几十个文件，却下载了项目成立 10 年来的每一次变更记录。

为了解决这个问题，项目在 fetch_project 函数中设计了一套“外科手术式”的精准 fetch 操作流程。

核心流程拆解

Python 脚本并没有一次性拉取所有数据，而是分四步走：快速搭架子 -> 精准捞数据 -> 时光倒流 -> 环境修复。

第一步：极速克隆 (Clone Latest)

  • 命令：git clone --depth 1 <repo_url> <target_dir>
  • 解读：
    这是整个流程的基石。参数 --depth 1 告诉 Git：“我只要最新的这一层代码，以前的历史我都不关心。”
  • 作用：
    这被称为 浅克隆 (Shallow Clone)。它能以最小的代价（通常只有几十 MB）快速把仓库的“架子”搭好，确立远程连接，生成 .git 目录，而无需下载漫长的历史提交记录。

第二步：精准补货 (Fetch Old Commit)

  • 命令：git fetch --depth 1 origin <commit_id>
  • 解读：
    这是高阶的一步。我们已经有了仓库架子，但那个包含漏洞的 commit_id 可能深埋在 5 年前的历史中，本地并没有。
    这条命令利用了现代 Git 服务器（如 GitHub）支持的特性，直接向服务器请求：“我只想要这个特定的 Commit Hash，把它以及它的文件快照给我，其他的父节点历史我依然不要。”
  • 作用：
    这相当于“按需补货”。Git 会将这个古老的版本作为一个“孤岛”下载到本地的 .git 数据库中。既拿到了我们急需的数据，又保持了本地仓库的轻量化。

第三步：时光倒流 (Checkout)

  • 命令：git checkout <commit_id>
  • 解读：
    数据下载到了 .git 目录（通常存在 FETCH_HEAD 中），但工作区的文件还是最新的。这一步是将工作区的文件“刷新”成漏洞版本的状态。
  • 作用：
    执行后，工作区正式回到“案发时间”。此时虽然处于 Detached HEAD（头指针分离）状态，但这对于代码分析和编译来说完全足够。

第四步：修复环境 (Apply Patch)

  • 命令：git apply <patch_path>
  • 解读：
    如果我们提前准备了补丁文件（位于 data/patches/），则应用它。
  • 为什么要这步？：
    这是漏洞复现中最痛的一点——“代码虽然回去了，环境却变了”。
    老旧的代码往往引用了已经关闭的 Maven 仓库，使用了不再兼容的 Gradle 插件，或者依赖了特定版本的编译器。我们不修改业务逻辑，只通过 Patch 修改构建脚本（如 pom.xml），确保这些“老古董”代码能在现代的机器上成功编译跑起来。

3. 总结

通过这套流程，IRIS 成功构建了一个高效的数据集构建 pipeline：

  1. Clone Latest: 只拿最新版，快。
  2. Fetch Specific: 只抓特定点，准。
  3. Checkout: 切换工作区，稳。
  4. Patch: 修正构建项，活。

这套 Git 组合拳极其精妙，它将原本可能需要数小时的下载任务缩短到了几秒钟，同时极大地节省了磁盘空间。对于从事软件仓库挖掘（Mining Software Repositories, MSR）的研究者来说，这绝对是必备的最佳实践。

PS：注意需要收集到精确的 commit_id 也就是存在漏洞的 SHA-1 哈希值作为版本号。

SSH安全协议

发表于 2026-01-18 分类于 Config

基础理论：Diffie-Hellman (DH) 密钥交换协议

在介绍SSH之前，首先了解DH协议，因为它是SSH能够安全协商密钥的基石。

  • 核心难题：如何在不安全的网络上，让两个人协商出一个只有他们知道的“密码”（会话密钥），而不用担心被旁人窃听？
  • 数学原理：基于离散对数问题的困难性。
    • 公式：
    • 正向计算容易：已知 ，算出 很快。
    • 反向计算极难：已知 ，想要算出指数 （私钥），在 足够大时，计算量是指数级的，现代计算机无法在有效时间内破解。
  • 作用：SSH利用DH算法，在客户端和服务器之间安全地生成一个对称密钥，用于后续的数据加密传输。

核心重点：SSH协议详解 (Secure Shell)

1. 什么是SSH？

SSH（Secure Shell）即“安全外壳”。它是基于公钥密码体系的安全应用协议，专为远程登录会话和其他网络服务提供安全性。

  • 主要目的：替代Telnet、rsh等不安全的明文传输协议。
  • 核心功能：加密（防窃听）、认证（防伪装）、完整性检查（防篡改）。

2. SSH的内部架构（三大子协议）

SSH不是一个单一的协议，而是由三个分工明确的协议组成的“协议栈”：

  1. SSH传输层协议 (Transport Layer Protocol)
    • 职责：负责最底层的脏活累活。包括算法协商（商量用什么加密）、密钥交换（DH算法）、服务器认证（确认服务器是真的）。
    • 结果：建立一个加密的、压缩的、保证完整性的安全通道。
  2. SSH用户认证协议 (User Authentication Protocol)
    • 职责：运行在传输层之上，负责鉴别客户端（用户）是谁。
    • 方式：支持口令认证（输入密码）、公钥认证（免密登录）等。
  3. SSH连接协议 (Connection Protocol)
    • 职责：在加密和认证都完成后，负责把加密隧道多路复用。
    • 功能：将一个物理连接逻辑上分为多个逻辑通道（Channel），分别处理终端会话、文件传输、端口转发等。

3. SSH的工作流程（7个步骤）

  1. 获取证书：客户端获取服务器的公钥证书（或已经存有服务器公钥）。
  2. 连接请求：客户端发起TCP连接（握手）。
  3. 服务器身份通告：服务器把自己的公钥发给客户端。
  4. 验证服务器：客户端验证这个公钥是不是真的服务器（防止中间人冒充）。
  5. 建立密钥 (DH)：双方通过Diffie-Hellman算法，协商出一个会话密钥（对称密钥）。
  6. 认证用户：建立加密隧道后，服务器验证客户端的身份（如输入密码）。
  7. 会话开始：使用SSH Tunnel进行加密通信。

4. 关键环节：如何验证服务器公钥的真实性？

客户端如何确认“发给我公钥的服务器真的是由于我要连接的那台服务器？”（防止中间人攻击）。主要有三种方法：

  • 方法一：物理拷贝 (最原始)
    • 用户直接带个U盘把服务器的公钥拷到客户端电脑里。安全但麻烦，不适合大规模使用。
  • 方法二：指纹核对 (最常用)
    • 流程：
      1. 首次连接时，客户端下载服务器公钥。
      2. 屏幕显示公钥的指纹 (Hash值)。
      3. 用户通过电话或其他渠道联系管理员核对指纹。
      4. 若指纹一致，用户输入“yes”信任该主机，公钥被保存到 known_hosts 文件中。
  • 方法三：PKI 认证 (最规范)
    • 通过权威的 CA 机构（PKI体系）来验证服务器证书的合法性。

5. SSH 的实际应用与风险

  • 默认端口：Linux系统中默认是 TCP 22 端口。
  • 功能扩展：不仅是远程黑窗口（Shell），还支持 scp/sftp（文件传输）、端口转发（跳板机/代理）。
  • 安全隐患：
    • 中间人攻击 (MITM)：如果在首次连接（TOFU, Trust On First Use）时没有仔细核对指纹，攻击者可能拦截连接并伪造公钥。
    • 拒绝服务攻击 (DoS)：因为SSH握手涉及复杂的加密计算（DH交换），消耗CPU资源大，攻击者可利用这一点耗尽服务器资源。

总结

SSH 是一个分层的协议，利用 DH算法 协商密钥，通过 三种方式 验证服务器身份，最终建立加密隧道替代 Telnet，保障 22端口 的远程管理安全。

加密与签名的区别

发表于 2026-01-18 分类于 密码学

私钥和公钥在数学逻辑上是可以“反过来”使用的（特别是在最经典的 RSA 算法中）。

但这两种“方向”所达到的安全目标是完全相反的，我们可以把这对密钥想象成一对神奇的数学钥匙：

数学原理：互为逆运算

在 RSA 这种经典的公钥密码体制中，公钥和私钥在数学上是成对生成的。

  • 规则：用A钥匙锁上的东西，只能用B钥匙打开；反之，用B钥匙锁上的东西，只能用A钥匙打开。

数学上没有规定谁必须叫“公钥”，谁必须叫“私钥”。只是在产生密钥后，我们人为地规定：

  • 公开给所有人的那把叫公钥。
  • 自己留着保密的那把叫私钥。

2. 两种方向，两种用途

正是因为它们可以“反过来”用，才衍生出了密码学的两大支柱功能：加密和签名。

情况 A：公钥加密，私钥解密（正常加密）

  • 操作：别人用你的公钥把数据锁起来。
  • 结果：因为只有你才有私钥，所以全世界只有你一个人能打开看。
  • 目的：机密性 (Confidentiality) —— 保护隐私，不让别人偷看。
  • 比喻：别人把信扔进你的信箱（公钥），只有你有钥匙（私钥）能打开信箱取信。

情况 B：私钥“加密”，公钥“解密”（数字签名）

  • 操作：你用你的私钥把一段数据（通常是摘要）锁起来（处理一下）。
  • 结果：因为公钥是公开的，全世界所有人都能用你的公钥打开它。
    • 你可能会问：“所有人都能打开，那还有什么保密性可言？”
    • 没错！这里根本不是为了保密！
    • 既然所有人都能用你的公钥解开，这就证明了——这段密文一定是用你的私钥锁上的。因为除了你的私钥，别人的私钥锁出来的东西，你的公钥是打不开的。
  • 目的：认证/防抵赖 (Authentication) —— 证明“这确实是我发的”。
  • 比喻：这就好比古代皇帝的“玉玺”（私钥）。皇帝在诏书上盖了章，全天下人（拿着公钥）一看印章纹路，就知道这是皇帝亲笔，不是别人伪造的。

3. 一个小小的专业修正

虽然我们为了理解方便，常说“数字签名就是用私钥加密”。但在严格的学术定义中：

  • 对于 RSA 算法：确实就是“私钥加密，公钥解密”的数学过程。
  • 对于其他算法（如 ECC、SM2、DSA）：虽然逻辑上是“私钥处理，公钥验证”，但数学过程并不是简单的加密反运算，而是专门设计的签名算法和验证算法。

总结：

  • 公钥 -> 私钥 = 为了秘密（只有你能看）。
  • 私钥 -> 公钥 = 为了证明（只有你能签）。

软考密码学考点概述

发表于 2026-01-18 分类于 密码学

软考常考的密码学基础知识、攻击类型以及主要的密码体制。以下是重要知识点：

一、 密码学基础概念 (Overview)

  • 定义与目标：密码学是研究信息安全保护的科学。主要目标是实现信息的保密性、完整性、可用性及抗抵赖性。
  • 组成：包含 密码编码学（研究加密/保护）和 密码分析学（研究破译/获取明文）。
  • 相关法律：提及了《电子签名法》（2005年）、商用密码算法公布（2006年）及《密码法》草案（2019年）。
  • 核心术语：
    • 明文：未加密的消息。
    • 密文：加密后的消息。
    • 加/解密算法：进行变换的运算规则。
    • 密钥：控制算法操作的关键参数。

二、 密码分析与攻击类型 (Attack Types)

根据攻击者拥有的信息量（前提条件），攻击类型分为五种（按攻击者能力从低到高）：

  1. 唯密文攻击：最困难，攻击者只有密文。
  2. 已知明文攻击：攻击者拥有一些“明文-密文”对。（注：一个安全的密码必须能经得起这种攻击）。
  3. 选择明文攻击：攻击者能制造明文并获取对应的密文（对攻击者有利）。
  4. 密文验证攻击：攻击者能判断某个密文解密后的结果是否合法。
  5. 选择密文攻击：最容易破译，攻击者能选定密文并获取对应明文（常见于攻击公钥体制和数字签名）。

三、 密码体制分类 (Cryptosystems)

1. 私钥密码体制 (Symmetric Key / 对称加密)

  • 特点：加密和解密使用相同的密钥。
  • 流程：双方必须事先通过安全渠道交换密钥。
  • 优缺点：
    • 优点：速度快
    • 缺点：密钥分配困难、密钥管理量大、无法认证源（难以实现抗抵赖）。
  • 常见算法：
    • DES：替换+移位、56位密钥、64位数据块、速度快、但56位密钥易被破解
    • 3DES：三重DES，两个56位密钥，K1和K2，较DES更安全
    • AES：美国标准，替代DES，安全性高
    • IDEA：128位密钥、64位数据块、较DES加密性更好
    • RC-5：RSA 数据公司很多产品使用RC5

2. 公钥密码体制 (Asymmetric Key / 非对称加密)

  • 特点：加密和解密使用不同的密钥（公钥和私钥）。
  • 原理：
    • 公钥：公开，用于加密。
    • 私钥：保密，用于解密。
    • 例子：甲给乙发消息，用乙的公钥加密，只有乙的私钥能解密。
  • 优缺点：
    • 优点：密钥分发方便、管理量少、支持数字签名。在公钥密码体制中，仅根据密码算法和加密密钥来确定解密密钥在计算上是不可行的。
    • 缺点：速度慢，计算量大，不适合加密大数据。
  • 常见算法：
    • RSA：基于大数分解，应用最广。公钥 (e,n) 私钥 (d,n) 。
    • ECC（椭圆曲线）、Elgamal、D-H（Diffie-Hellman）、背包算法。

3. 混合密码体制 (Hybrid System)

  • 目的：结合对称加密的“快”和非对称加密的“密钥分发方便”。
  • 工作流程：
    1. 发送方随机生成一个对称密钥。
    2. 用对称密钥加密明文消息（数据传输快）。
    3. 用接收方的公钥加密这个对称密钥（数字信封）。
    4. 将加密后的消息和加密后的密钥一起发送。
    5. 接收方先用私钥解出对称密钥，再用对称密钥解密消息。

这张PPT主要详细介绍了四种常见的对称加密算法（DES、3DES、IDEA、AES）的具体参数和工作原理。以下是为您总结的核心知识点：

四、常见密码算法

1. DES 算法 (Data Encryption Standard)

  • 类型：分组加密算法。
  • 分组长度：支持 64比特 的明文块加密。
  • 密钥长度：56比特。
  • 特点：由于密钥较短（56位），在现代算力下安全性较低，已逐渐被淘汰。

2. 三重DES (3DES / TDEA)

  • 原理：为了提高安全性，使用DES算法对明文进行 “加密 - 解密 - 加密” 的三次操作。
  • 操作流程：
    • 加密：明文 -> (用K1加密) -> (用K2解密) -> (用K3加密) -> 密文。
    • 解密：密文 -> (用K3解密) -> (用K2加密) -> (用K1解密) -> 明文。
  • 密钥规则：通常情况下，K1 和 K3 是相同的密钥（即使用两个不同的密钥K1和K2进行三次运算）。

3. IDEA 算法 (International Data Encryption Algorithm)

  • 类型：分组加密算法。
  • 分组长度：明文和密文分组均为 64比特。
  • 密钥长度：128比特（比DES更安全）。
  • 设计思想：混合使用来自不同代数群中的运算。

4. AES 算法 (Advanced Encryption Standard)

AES是用来替代DES的新一代标准，PPT中列出了该算法必须满足的标准要求：

  • 公开性：算法无密级，描述必须完全公开披露。
  • 免费性：必须可以在世界范围内免费使用。
  • 分组长度：支持至少 128比特 的分组。
  • 密钥长度：支持 128、192 和 256比特 的密钥长度。

总结对比表：

算法 分组长度 密钥长度 关键特征
DES 64 bit 56 bit 早期标准，现已被认为不够安全。
3DES 64 bit 112 bit* (通常) “加密-解密-加密”模式，过渡方案。
IDEA 64 bit 128 bit 混合代数运算设计。
AES ≥128 bit 128/192/256 bit 现行标准，公开、免费、强度高。

(注：3DES如果K1=K3，有效密钥长度通常认为是112位)

5.国产密码算法

  • 国产密码算法：指由国家密码研究相关机构自主研发、具有相关知识产权的商用密码算法。
算法名称 算法类型 关键参数/技术细节 主要用途/备注
SM1 对称加密 分组长度：128比特
密钥长度：128比特		 硬件实现为主，通常作为SM4的非公开版本背景知识
SM2 非对称加密 基于椭圆曲线（ECC）
推荐使用素数域 256位 椭圆曲线		 功能全面：包括公钥加密、密钥交换协议、数字签名算法。
SM3 杂凑算法 (Hash) 杂凑值（摘要）长度：256比特 类似于国际上的SHA-256。
SM4 对称加密 分组长度：128比特
密钥长度：128比特		 无线局域网标准算法，参数与SM1一致，但已公开。
SM9 标识密码 标识密码算法 (IBC) 基于身份的密码技术（例如将邮箱或手机号直接作为公钥）。

为了方便理解和记忆，可以将国产算法与国际通用算法进行对标：

  • SM1 / SM4 (对称) AES-128 (两者都是128位分组和密钥)
  • SM2 (非对称) ECC / RSA (但在相同安全强度下，SM2比RSA密钥更短，速度更快)
  • SM3 (哈希) SHA-256 (输出长度相同)

6.习题

利用公开密钥算法进行数据加密时，采用方式是：发送方用公开密钥加密，接收方用私有密钥解密。
